# REGAIN 要件定義書：フィジポッ（Physipo）ver1.0

## 0. 本書について
- 本書は「REGAIN：AIアプリ開発のための要求定義書 ver0.8」と、REGAIN標準の非機能要件構成をもとに作成した要件定義書である。
- 開発はAIエージェント（Claude Code Web）による実装を前提とし、人によるコード編集は行わない。クリエイターはターミナル・コマンドプロンプト・CLIを使用せず、すべての操作はAIエージェントへの指示、またはGitHub／Neon／Vercelの各ブラウザ管理画面から行う。

## 1. アプリ概要
- アプリ名：フィジポッ（Physipo）
- 目的：回復期病院に勤務する理学療法士が、日々の患者対応（カルテ内容）を整理・蓄積し、後から似た症例やアプローチを検索・参照できるようにする。
- 想定利用者：Day1時点では本人1名（role: player）。将来的に複数の記録者・管理者（role: staff／coach）が加わることを想定し、非機能要件のロール設計をそのまま採用する。
- 主な利用シーン：仕事終了後、帰宅中の電車・バス内でスマホから入力。後日、PCで症例を検索・参照。編集・削除・テンプレート管理はPCのみ。

## 2. 画面一覧

| 画面ID | 画面名 | 主な利用デバイス | 概要 |
|---|---|---|---|
| S1 | ログイン画面 | スマホ／PC共通 | 合言葉のみによるログイン（本人専用のため氏名選択なし） |
| S2 | セッション入力画面 | スマホ最適化 | 疾患区分別のセッション記録入力 |
| S3 | 閲覧・検索画面 | レスポンシブ（PC・タブレット推奨） | 症例の一覧・検索・展開表示、テンプレート保存操作 |
| S4 | 編集専用画面 | PC・タブレット専用 | 過去セッションの編集・削除 |
| S5 | テンプレート管理画面 | PC・タブレット専用 | テンプレートの一覧・命名・削除 |

## 3. 機能要件（画面ごと）

### 3.1 S1：ログイン画面
- 本人専用アプリのため氏名選択は行わず、合言葉（パスワード）の入力欄のみを表示する。
- メールアドレス入力・パスワードリセットなど高度なUIは設けない。
- 合言葉が正しければ、登録済みの利用者（role: player）で自動的にログインする。ログイン後の画面には利用者名が表示される。
- 認証エラー時は「合言葉が正しくありません」等、原因を特定させない汎用エラーメッセージを表示する。

### 3.2 S2：セッション入力画面（スマホ最適化）
**症例の選択・作成**
- ログイン後、まず「症例」を選択（継続中の患者の場合）または新規作成する。
- 症例には個人情報を含まない任意の症例コード（例：イニシャルや任意の番号）を記録者自身が入力する。氏名・生年月日等の個人情報は登録しない。
- 同一症例に対する2回目以降のセッションでは、直前セッションのROM・MMT数値が自動的にセットされた状態で表示され、変化がなければそのまま保存、変化があった項目だけ編集する。前回と同じ値の項目も見た目上区別せず表示する。初回のみ全項目をゼロから入力する。

**共通入力項目（脳血管／廃用／運動器、毎回入力）**
- 年齢
- 病名（複数タグ可。過去登録タグから選択、または新規追加可。自分が登録した範囲内で略語・別名などの表記ゆれをある程度吸収する簡易サジェスト）
- 介入◯日目
- ROM（股関節屈曲・伸展・外転・内転、膝関節屈曲・伸展、足関節背屈・底屈の8項目×左右＝16項目、スライダー入力・5度刻み）
- MMT（股関節屈曲・伸展、膝関節屈曲・伸展、足関節背屈・底屈の6項目×左右＝12項目、スライダー入力）
- ROM・MMTは初期セットに加え、必要に応じて部位を追加可能

**疾患区分別の専用項目**
- 脳血管：Brunnstrom Stage（上肢のみ）／感覚検査（触覚、5段階選択：正常・軽度鈍麻・中等度鈍麻・高度鈍麻・消失）／MAS（上肢屈曲のみ）
- 廃用：専用項目なし（共通項目のみ）
- 運動器：疼痛スケール（VAS/NRS、スライダー0〜10）／荷重制限の状況（数値または自由記述）／歩行距離・歩行速度（自由記述）

**テキストデータ（必須）**
- 介入内容：選択式・複数選択可（一覧から選択、新規メニュー追加可。選択数の上限なし、1つ以上必須。選んだものはタグとして並べ、個別に外せる）
- Assessment：自由記述（次に似た症例が来たときに参照したい評価・判断・工夫）

**入力ルール**
- 基本的に全項目を毎回入力必須とする。
- 病名タグ・介入内容のサジェストは、Day1では自分の過去入力頻度順のシンプル版とする（本格的な医学用語辞書型の予測変換・表記ゆれ吸収はDay1では実装しない）。

**テンプレート読込**
- 新規セッション入力時、保存済みテンプレートを選択すると、ROM・MMT・Brunnstrom等の数値、病名タグ、疾患区分が一括入力される。異なる部分のみ修正すればよい。

### 3.3 S3：閲覧・検索画面
- 一覧（表形式）のみで完結。別の詳細ページには遷移しない。
- 一覧の行をタップ／クリックすると、その場で行が展開し、Assessmentの全文が読める。
- 表示項目：病名タグ、疾患区分、年齢、Assessmentの冒頭一部（展開すると全文）。
- 検索・絞り込み軸：病名（タグ）／疾患区分（脳血管・廃用・運動器）／介入内容／キーワード検索（Assessment本文等）。
- ROM・MMT・VAS等の数値は色分け等の視覚加工をせず、そのままドライに表示する。グラフ表示・比較機能は設けない。
- 展開表示に「このケースをテンプレートとして保存」ボタンを配置する。押下すると、そのセッションのROM・MMT・Brunnstrom等の数値、病名タグ、疾患区分をテンプレートとして保存できる（Assessment等の自由記述文はテンプレートに含めない）。
- 閲覧範囲：role=playerは自分（user_id）が記録したセッションのみ。role=staff／coachは全利用者のセッションを横断的に閲覧できる。

### 3.4 S4：編集専用画面（PC・タブレット専用）
- 過去に入力したセッションの記録を編集・削除できる。
- 削除時は「本当に削除しますか？」という確認メッセージを表示する。
- スマホからはアクセスできないようにする（画面幅等で判定し、専用の案内を表示する）。
- 編集・削除できる範囲：role・staff／coachともに、既定では自分（user_id）が記録したセッションのみとする（他者記録の閲覧はS3で可能だが、編集・削除は不可）。この権限設計はDay4のNeon Auth・RLS導入時に本格的に見直す。

### 3.5 S5：テンプレート管理画面（PC・タブレット専用）
- 自分が保存したテンプレートの一覧を閲覧・管理できる。
- テンプレートの命名・削除が可能。
- 複数のテンプレートを保存・切り替え可能。
- テンプレートは保存した本人（user_id）のみアクセス可能。
- Day1実装範囲：作成・読込・削除の基本機能のみ。テンプレート検索・共有機能は将来の追加候補とする。

## 4. データ構造

### 4.1 テーブル一覧

| テーブル名 | 概要 |
|---|---|
| users | ログイン可能な利用者（id・氏名・role） |
| cases | 症例（匿名の症例コード、疾患区分、記録者） |
| sessions | セッション記録（症例に紐づく1回分の介入記録） |
| tags | 病名タグのマスタ（利用者ごとに登録） |
| session_tags | セッションと病名タグの中間テーブル |
| intervention_menu | 介入内容（訓練メニュー）のマスタ |
| templates | テンプレート（初期値セット） |

### 4.2 各テーブルの詳細

**users**
- id（PK）
- name：氏名
- role：'player' ／ 'staff' ／ 'coach'（既定はplayer。staffとcoachは同一権限として扱う）
- created_at

**cases（症例）**
- id（PK）
- user_id（FK→users、症例を作成した記録者）
- case_code：匿名の症例コード（記録者が任意入力。個人情報は含めない）
- disease_category：'脳血管' ／ '廃用' ／ '運動器'
- created_at／updated_at

**sessions（セッション記録）**
- id（PK）
- case_id（FK→cases）
- user_id（FK→users、記録者）
- intervention_day：介入◯日目
- age：年齢
- rom_data：ROM16項目をJSONBで保持（部位追加にも対応できる可変構造）
- mmt_data：MMT12項目をJSONBで保持（同上）
- disease_specific_data：疾患区分別の専用項目をJSONBで保持（Brunnstrom／感覚検査／MAS、またはVAS／荷重制限／歩行距離・速度など）
- intervention_content：介入内容（選択値、自由入力の新規メニューも許容）。複数選択時は「、」区切りの文字列（互換用）
- intervention_contents：介入内容の配列（text[]、複数選択の正式な保存先。過去データはマイグレーションで1件の配列としてコピー）
- assessment：Assessment本文（自由記述）
- created_at／updated_at

**tags（病名タグマスタ）**
- id（PK）
- user_id（FK→users、登録者）
- name：タグ名
- created_at

**session_tags（中間テーブル）**
- session_id（FK→sessions）
- tag_id（FK→tags）

**intervention_menu（介入内容マスタ）**
- id（PK）
- user_id（FK→users）
- name：メニュー名
- created_at

**templates（テンプレート）**
- id（PK）
- user_id（FK→users、保存者）
- name：テンプレート名
- disease_category：疾患区分
- template_data：ROM・MMT・Brunnstrom等の数値、病名タグをJSONBで保持
- created_at／updated_at

### 4.3 設計上の補足
- 「症例」は要求定義書には明記のない概念だが、「2回目以降はROM・MMTの前回値を自動反映する」という要件を実現するために導入した。症例コードは記録者が任意に付与する匿名コードとし、氏名・生年月日等の個人情報は保持しない。
- Day4でNeon Auth・RLSを導入するまでは、5.5節の方針により個人情報・健康情報など機微なデータは登録しないことを前提とする。

## 5. 非機能要件（REGAIN標準構成）

本要件定義書における role=player は日々セッションを記録する一般利用者（Day1では本人1名）、role=staff／coach は複数記録者のデータを横断閲覧できる管理者的利用者を指す。Day1時点の実利用者は1名のみだが、将来の利用者追加に備え、以下の構成をそのまま採用する。

### 5.1 開発方式
- コーディングはAIエージェント（Claude Code Web）で実施し、人によるコード編集は行わない。
- クリエイターはターミナル・コマンドプロンプト・CLIを使用しない。すべての操作は、AIエージェントへの指示か、各サービス（GitHub／Neon／Vercel）のブラウザ管理画面から行う。
- 実装完了時、AIエージェントは `SESSION_SECRET` 用のランダムな文字列（32バイトをbase64エンコードしたもの）を1つ生成し、チャット上に表示する。この文字列はリポジトリ内のいかなるファイルへも書き込まない。

### 5.2 データベース
- Neon（PostgreSQL）を使用する。
- テーブル設計は4節のデータ構造に基づいて作成する。
- アプリからNeonへの接続には、Vercel連携で設定される `DATABASE_URL` を使用する。
- データベースへの読み書きは、サーバー側から `@neondatabase/serverless` を使って行う。
- `DATABASE_URL` はブラウザへ公開せず、サーバー側だけで使用する。
- 各データには、将来ユーザーごとのアクセス制御ができるよう `user_id` を持たせる。
- Neon AuthとRLS（Row Level Security）はDay4で導入し、本格的な認証・アクセス制御へ改修する。

### 5.3 ホスティング・デプロイ
- Vercelでホスティングする（GitHubリポジトリと連携した自動デプロイ）。
- mainブランチを本番環境とする。

### 5.4 対応デバイス
- スマホ最適化（モバイルファースト）：S2セッション入力画面
- PC・タブレットでも閲覧可能（レスポンシブ対応）：S3閲覧・検索画面
- 特にPC・タブレット最適化を優先する画面：S4編集専用画面、S5テンプレート管理画面

### 5.5 セキュリティ・認証設計（シンプル構成）

**認証UI（ログイン画面）**
- 本人専用アプリのため氏名選択は行わない。合言葉（パスワード）の入力欄のみを表示する。
- メールアドレス入力・パスワードリセットなどの高度なUIは不要。

**裏側の実装**
- Day2時点ではNeon Authを使用せず、全員共通の合言葉を使った簡易認証とする。
- `users` テーブルには `id`・`name`・`role` を持たせ、パスワードや合言葉は保存しない。
- 合言葉はVercelのサーバー専用環境変数 `APP_SHARED_PASSWORD` で管理する。
- ログイン時は、入力された合言葉をAPI RouteまたはServer Actionへ送り、サーバー側で環境変数と照合する。
- 合言葉が一致した場合、氏名選択なしで登録済みの利用者（role: player）を自動的にログイン対象とする（`users` テーブルのroleがplayerである最初の1件）。
- ログイン成功後は、ユーザーIDとroleを改ざんできない署名付きセッションCookieで管理する。
- Cookieは `HttpOnly`・`Secure`・`SameSite=Lax` を基本とし、認証情報をlocalStorageへ保存しない。
- データの読み書きはサーバー側で行い、毎回セッションを確認してからユーザーごとにデータを絞り込む。
  - roleが `player` の場合 → `WHERE user_id = 自分のID` で自分のデータのみ表示（S3閲覧・検索、S4編集専用、S5テンプレート管理いずれも同様）
  - roleが `staff`／`coach` の場合 → S3閲覧・検索画面では全利用者のデータを表示。S4編集専用画面・S5テンプレート管理画面は自分が記録したデータのみを対象とする。
- この簡易認証は初回デプロイ用の暫定構成とし、Day4でNeon Auth・ユーザーごとのセッション・RLSを使った構成へ改修する。
- Day1時点は本人1名（role: player）のみの利用を前提とし、氏名選択も廃止したため、共有の合言葉を知っていても別の利用者になりすますことはできない。それでもDay4の改修までは個人情報・健康情報などの機密データは登録しない。

**初期データ**
- 本人専用アプリのため、利用者（role: player）1名分のデータのみを `users` テーブルに投入するSQLを作成する。
- `users` テーブルにはパスワードを保存しない。
- 共通の合言葉は `APP_SHARED_PASSWORD` としてVercelの環境変数に設定する。

### 5.6 環境変数
- `DATABASE_URL`：Neonへの接続情報。NeonとVercelの連携時に自動設定される。
- `APP_SHARED_PASSWORD`：全員共通の合言葉。Vercelで手動設定する。
- `SESSION_SECRET`：セッションCookieへの署名に使用する十分に長いランダムな文字列。Vercelで手動設定する。この文字列はAIエージェント（Claude Code Web）が実装完了時に生成・表示し、クリエイターがVercelの管理画面へ貼り付ける。クリエイターがターミナルやコマンドプロンプトで生成する手順は使用しない。
- 3つともサーバー専用とし、`NEXT_PUBLIC_` を付けない。
- `.env` ファイルや接続情報をGitHubへアップロードしない。

### 5.7 UI／デザイン方針
- 配色（Huemintで生成・確定）：背景＝白（#FFFFFF）、メインカラー＝薄いブルー（#7EC8E3）、アクセントカラー1＝ダークネイビー（#131727）、アクセントカラー2＝コーラルレッド（#DD6868）。
- グラフによるデータ可視化、数値の色分け等の視覚的加工は行わない（ドライな表示を優先）。
- 複雑な機能は省き、シンプルな構成を優先する。

## 6. ドキュメント成果物要件（実装完了後に作成）

本要件定義書とは別に、実装完了後（コーディング後）に以下の2つのMarkdownドキュメントを作成し、コードと共にリポジトリへpushすること。本タスクではこれらのドキュメント自体は作成しない。

### 6.1 デプロイ手順書（DEPLOYMENT.md）
- 読者は超初心者であることを前提とし、どのサービスのどの画面でどういう操作をするのかを丁寧に説明する構成とする。
- 記載する内容：
  1. Neonプロジェクトの作成手順（データベース作成、接続情報の確認）。プロジェクト作成時の設定値（Region、Neon Authの設定方針＝Day1では有効化しない、など）も記載する。マイグレーション用SQLは `db/schema.sql` と `db/seed.sql` に配置する前提とし、初心者でも迷わないよう、GitHub上でこれらのファイルへ辿り着く手順（リポジトリ画面での操作）も記載する。
  2. Vercelプロジェクトの作成手順（GitHubリポジトリのインポート）。インポート→環境変数設定→デプロイの順で記載する。
  3. Neon×Vercelの連携手順。Vercel Marketplace経由ではなく、環境変数 `DATABASE_URL` を手動で設定する方式とし、Neon側でのURL取得手順も記載する。
  4. `APP_SHARED_PASSWORD` と `SESSION_SECRET` をVercelの環境変数へ設定する手順。`SESSION_SECRET` は実装完了時にAIエージェントがチャット上へ生成・表示済みである前提とし、「表示された文字列をコピーしてVercelの環境変数へ貼り付ける」と記載する。opensslなど、クリエイターにターミナルやコマンドプロンプトを開かせる手順は記載しない。生成した文字列そのものを、DEPLOYMENT.mdやソースコードなどリポジトリ内のファイルへ記載しない。

### 6.2 動作確認手順書（VERIFICATION.md）
- 3節の機能要件に記載した操作（ログイン、疾患区分別のセッション入力、ROM・MMTの前回値継承、病名タグの登録・選択、閲覧・検索・キーワード検索、展開表示、PCでの編集・削除（確認ダイアログ含む）、テンプレートの作成・読込・削除、スマホ／PCでのレスポンシブ表示など）が正しく動作するかどうかを、1つずつ確認できる手順書とする。
- Markdown形式で作成し、コード実装完了後にコードと共にリポジトリへpushする。

## 7. スコープ外（Day1で実装しないこと）

- 閲覧画面での現在の症例と過去の症例の数値比較機能
- 一覧とは別の詳細ページ（一覧内の展開表示で対応する）
- 本格的な医学用語辞書レベルの予測変換・表記ゆれ吸収（病名タグを含む。自分が登録した範囲を超える外部辞書レベルの対応はDay1では実装しない）
- テンプレートの検索・共有機能

## 8. 用語集
- 症例（case）：1人の患者に対する一連のセッション記録の集合。匿名の症例コードで識別する。
- セッション：1回の介入（患者対応）ごとに入力される記録単位。
- 疾患区分：脳血管／廃用／運動器の3区分。
- role：player＝一般記録者（自分のデータのみ）、staff／coach＝管理者（全データを閲覧可能）。
